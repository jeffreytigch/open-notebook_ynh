# YunoHost Packaging Reference (condensed)

A practical, project-scoped digest of the YunoHost packaging rules we must
follow. It is **not** a substitute for the official docs
(<https://doc.yunohost.org/en/dev/packaging/>); it exists so the implementation
can proceed without re-reading everything, and so reviewers can see the plan is
grounded in the real rules.

## 1. Format and policy

- We target **packaging format 2** (TOML `manifest.toml`) with
  **`helpers_version = "2.1"`**.
- The package **must** closely follow the
  [`example_ynh`](https://github.com/YunoHost/example_ynh) template. The
  packaging policy explicitly warns that generated/AI packages that deviate
  from the template are rejected, and that the maintainer must be able to
  explain every line. We will therefore mirror `example_ynh` structure and
  idioms, and document each non-obvious choice in
  [`architecture-decisions.md`](architecture-decisions.md).

## 2. Repository structure (what we must ship)

```
manifest.toml            # required — the "ID card"
tests.toml               # required — package_check scenario control
LICENSE                  # license of the PACKAGE (AGPL-3 recommended)
README.md (+ README_fr.md)# auto-generated by yunohost-bot for YunoHost-Apps repos
config_panel.toml        # optional — only if we ship a config panel
conf/                    # templates rendered by the scripts
  nginx.conf
  systemd.service (we will ship several)
  .env                   # our app config template
doc/
  DESCRIPTION.md (+_fr)  # shown in the catalog
  ADMIN.md (+_fr)
  PRE_INSTALL.md, POST_INSTALL.md, PRE_UPGRADE.md, POST_UPGRADE.md
  screenshots/
scripts/
  _common.sh install remove upgrade backup restore change_url [config]
.github/
  ISSUE_TEMPLATE.md, PULL_REQUEST_TEMPLATE.md     # copied from example_ynh
  workflows/                                       # our own quality gates (see §7)
```

Sourcing rules for scripts:

- `install`, `remove`, `upgrade`, `change_url`, `config` do `source _common.sh`
  then `source /usr/share/yunohost/helpers`.
- `backup` and `restore` **source `../settings/scripts/_common.sh`** (they run
  from a different context) then `/usr/share/yunohost/helpers`.
- Every script wraps work in `ynh_script_progression "..."` and ends with a
  completion message. Scripts run under `set -eu` (except `remove`, which does
  not use `-e`).

## 3. `manifest.toml` — what we must fill in

- `packaging_format = 2`, `id = "open_notebook"` (lowercase; used for the
  system user, `/etc/yunohost/apps/...`, nginx conf), `name` (≤23 chars),
  `description.en`/`.fr` (≤150 chars), `version = "1.15.0~ynh1"`,
  `maintainers`.
- `[upstream]`: `license = "MIT"`, `website`, `code`, `userdoc` (upstream docs),
  `admindoc`, `demo`.
- `[integration]`: `yunohost = ">= 12.1"`, `helpers_version = "2.1"`,
  `architectures = ["amd64","arm64"]`, `multi_instance`, `ldap`, `sso`, `disk`,
  `ram.build`, `ram.runtime`. The `ldap`/`sso` values are decided in ADR-004.
- `[install]` questions: `domain` (type `domain`), `path` (type `path`),
  `init_main_permission` (type `group`, default `all_users` or `visitors`),
  plus any app-specific questions. A `password`-typed question is **not** stored
  as a setting (we use it only to seed the app).
- `[resources]` (§4).

## 4. Resources we will use

Provisioning runs **before** `install`; deprovisioning runs **after** `remove`.
Values become settings and are templated as `__UPPERCASE__` (e.g. `$data_dir`
→ `__DATA_DIR__`) or referenced as shell vars (`$port`, `$install_dir`).

| Resource | Our use | Notes |
|---|---|---|
| `sources` | `main` = open-notebook tag tarball; `surreal` = SurrealDB **v2** binary (arch-specific); `uv` = pinned `uv` binary (arch-specific). | `sha256` required per source (per `amd64`/`arm64`). `autoupdate.strategy` — **but** SurrealDB must not follow v3 (ADR-002). |
| `apt` | `ffmpeg`, `curl`, build prerequisites as needed. | There is **no** Python resource → Python comes from `uv` (preferred) or apt. |
| `system_user` | Runs all services. | `allow_email` only if needed (not by default). |
| `install_dir` | `/var/www/open_notebook`. | Holds the checkout, `.venv`, built frontend. Re-created by installing; **not** backed up by default. |
| `data_dir` | `/home/yunohost.app/open_notebook`. | The real `/data` (DB + uploads + podcasts + sqlite). This **is** the backup target (ADR-003). |
| `permissions` | `main.url = "/"`. | Gates the app behind SSOwat; see ADR-004. |
| `ports` | `main` (frontend), `api`, `surreal`. | Internal reverse-proxy ports; not exposed to the internet. |
| `nodejs` | version `22`. | Provides `$path_with_nodejs` / `$nodejs_dir` for our systemd units. |

Resources we will **not** use: `database` (only mysql/postgresql — SurrealDB is
not supported, so we install its binary ourselves), `php`, `ruby`, `go`,
`composer`.

## 5. Helper conventions (helpers 2.1)

Naming we must use (renamed from 2.0):

| Purpose | 2.1 helper |
|---|---|
| Render config template | `ynh_config_add --template= --destination=` |
| Install/refresh nginx conf | `ynh_config_add_nginx` / `ynh_config_remove_nginx` |
| Install/refresh systemd unit | `ynh_config_add_systemd` / `ynh_config_remove_systemd` |
| logrotate | `ynh_config_add_logrotate` / `ynh_config_remove_logrotate` |
| fail2ban | `ynh_config_add_fail2ban` / `ynh_config_remove_fail2ban` |
| Service action | `ynh_systemctl --service= --action=` |
| Backup a path | `ynh_backup "<path>"` |
| Restore a path | `ynh_restore "<path>"` (symmetric with `ynh_backup`) |
| Remove files | `ynh_safe_rm "<path>"` (positional) |
| Change URL | `ynh_config_change_url_nginx` |
| Version guards | `ynh_app_upgrading_from_version_before`, `ynh_app_upstream_version_changed` |
| Detect CI | `ynh_in_ci_tests` |

Note the changed backup/restore semantics: `ynh_restore` now restores a single
path (old `ynh_restore_file`); "restore everything" is `ynh_restore_everything`.
Backup/restore scripts should not hand-delete `/var/log/$app` (the core does it
on `remove --purge`).

## 6. `tests.toml` and how app testing really works

- **There is no official GitHub Action** for YunoHost app testing. Do not look
  for one.
- The official test suite is **`package_check`**, driven by **`yunorunner`** on
  YunoHost's infrastructure. It installs the app in a throwaway container and
  runs install / remove / reinstall (root, subpath, private, multi-instance),
  upgrade (incl. from pins), **backup/restore**, and **change_url**, then
  grades a **quality level 0–8**.
- **Official CI:** `https://ci-apps.yunohost.org/` — auto-triggered after each
  commit to the default branch.
- **Dev CI:** `https://ci-apps-dev.yunohost.org/` — for PRs, triggered by a
  YunoHost-Apps member commenting `!testme`.
- **Static lint:** [`YunoHost/package_linter`](https://github.com/YunoHost/package_linter)
  (`python3 package_linter.py <app>_ynh`), plus JSON-schema validation of
  `manifest.toml` (`YunoHost/apps/schemas/manifest.v2.schema.json`).
- `tests.toml` mostly just needs a header and `[default]`; add `args.*`
  overrides and a `test_upgrade_from.<sha>.name` entry once a version is
  released. Syntax:

  ```toml
  test_format = 1.0
  [default]
    args.<question> = "<value>"
    test_upgrade_from.<commit>.name = "Upgrade from 1.15.0"
  ```

## 7. CI/CD we can actually add on GitHub

Since the *official* CI lives on YunoHost's servers, our GitHub Actions
complement it. Planned (`docs/PLAN.md` Phase 6):

1. **`lint.yml`** — the highest-value local gate:
   - `package_linter` (clone and run),
   - manifest/tests schema validation against `YunoHost/apps` schemas,
   - `shellcheck` + `bash -n` on `scripts/*`,
   - TOML/YAML validation (`taplo`, `yamllint`).
2. **`dependabot.yml`** — keep action versions fresh.
3. Optional: a workflow that pulls upstream release info to help maintain pins
   (note: SurrealDB must stay on v2).

We deliberately **do not** try to emulate `package_check` in GitHub Actions —
that would be a fragile container-in-container setup. We rely on the official
CI dashboards for integration testing.

## 8. Publishing to the catalog

- Catalog repo: `https://github.com/YunoHost/apps`, file **`apps.toml`**.
- Add an entry (alphabetical) with `state` (`working`), a `category`, optional
  `antifeatures`, and the repo `url`; add a logo; open a PR. Do **not** set
  `level` (the bot derives it from official CI weekly).
- The catalog publishes the **HEAD of the default branch**, so develop on
  branches and keep `main` releasable.
- `autoupdate.strategy` in the manifest lets the infra propose upstream bumps
  automatically (replacing the old per-repo `updater.yml` workflow).

## 9. Translation

Per-app strings are **not** in Weblate. Translations are Git-based: provide
`description.fr`, `doc/*_fr.md`, etc. We will ship French alongside English.
